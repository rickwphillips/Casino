1. What this document fixes, and what it does not

Stage 3 builds three distinct visual directions. A single identity spec written before that choice would either pre-empt it or say nothing.

So this spec fixes structure and leaves skin alone. It settles the vocabulary: how many token roles exist, what each one means, which card states the rules require the player to tell apart, and what the real geometry is. Each Stage 3 direction then instantiates the same token names with different values. Swapping directions becomes editing CasinoTheme.Palette, not rebuilding the UI.

The palette in section 3 is therefore a reference instantiation, the one shipping in v1.0.0, not a recommendation. It is here so the directions have a baseline to be measured against.

2. Token architecture

Governs: Assets/Scripts/CasinoTheme.cs

Two tiers, already implemented in Stage 1. The rule that makes it work is that UIManager may only ever name a semantic token. It must never reference a raw hue, and never a raw literal.

TierExampleAnswersWho edits it
Palette Palette.GoldDeep What hue is this? A visual direction. Wholesale re-skins happen only here.
Semantic ButtonPrimary What does this element mean? This spec. Adding a role is a design decision, not a color decision.

Why the tiers are worth the indirection

Stage 1 found four pairs of identical colors reached by different code paths, including the move banner and the round summary title, and the score panel stats and the summary columns. They were the same by coincidence, and a palette edit would have desynchronised them. Naming Headline and PlayerAccent once makes that coincidence a guarantee.

InvisibleHitArea is alpha 0.01, not 0. A Unity Image with zero alpha stops receiving raycasts, so a build stack would become unclickable. It looks like a rounding artifact and is load-bearing.

4. Typography

Every glyph in the game is currently the Unity default sans at one weight. Card ranks, the hint line, the score readout, and the button labels are all the same face, separated only by size. There is one font asset in the project: none.

A TMP font asset is the single largest visual lever available, and it is a Stage 5 deliverable. What Stage 2 fixes is the set of roles a direction must supply, so no direction ships a face that cannot do all four.

RoleJobRequirementSize now
RankCard rank and suit glyphUnambiguous 6/9 and 10; must carry a suit pip at small size; the only text that is read at a glance rather than parsed30 / 21 mini
InterfaceButtons, hint line, turn stateLegible at 13 to 20 units on a saturated ground13–20

Known trap

TMP text metrics do not match CSS. A Stage 3 mockup that sets a rank at 30px will not produce identical bounds in Unity, because TMP measures from the font's own ascender and descender rather than a CSS line box. Treat mockup type sizes as intent, and the layout-report.txt diff in Stage 4 as truth.

5. Space and the canvas

Governs: UIManager.EnforceLayout()

The reference canvas is 1280 × 720 with matchWidthOrHeight = 1. With the Game view pinned to the same size, canvas units equal screen pixels exactly, so every number below is directly checkable against layout-report.txt.

The layout uses no spacing scale at present. Observed gutters include 10, 12, 14, 16, 20 and 30, chosen ad hoc. Proposed scale, in canvas units, with everything a multiple of 4:

What the 1280 × 720 baseline exposed

These offsets were tuned against a 600-unit-tall canvas. At 720 the whole left half of the board is empty felt, the table row sits 20 units right of centre for no reason anyone remembers, and the action stack is separated from the score panel it belongs with by roughly 160 units of nothing. The table row is 560 wide holding four 80-wide cards. None of this is new damage; it is layout debt that was previously hidden by the canvas stretching. Stage 4 owns it.

6. Card anatomy

Governs: CardUI

A card is an Image with a single TMP string centred on it, for example 10♥. There are no corner indices, no pips, and no court art. Specimens below are rendered at the exact unit sizes the engine uses.

The build stack is not a box with a header. It is a physical fan: 16 units of horizontal step per card, alternate cards dropped 3 units, and a rotation of 2 degrees per position away from centre, with a 30-unit owner-coloured badge pinned to the top right carrying the declared value. That is a good idea already in the code and every direction should keep it.

Requirement for every direction

Corner indices are not decoration here. Cards in a build overlap with only 16 units showing, so the centred glyph on every card except the last is hidden. A player cannot currently read what is in a build without opening it. Any direction must put the rank in the top-left corner, inside 16 units.

Sweeps are optional and partial: the played card may take several sets at once and the player chooses. Nothing shows which table cards the held card could take before selecting it.

Two collisions to resolve, not restyle

Selected means two opposite things. HighlightTableCardsForCapture reuses SetSelected(true) to show what the AI is about to take. The identical Sky tint and 1.15 scale therefore reads as both "you picked this" and "the opponent is taking this." These need separate signals.

Suggested means two different things. It marks the Suggest hint's recommended play, and separately marks hand cards that can take a chosen table card. One is advice, the other is availability. A direction that gives them the same green inherits the ambiguity.

Rules for any direction

  • Never encode state in hue alone. Pair every tint with a second channel: scale, outline, elevation, or a corner mark. Owner colour on builds is the one place hue currently carries meaning by itself.
  • Advice and availability must differ. Suggest is optional guidance; capturability is a fact about the board.
  • Player action and opponent action must differ. See the collision above.
  • Keep the physical fan. Builds read as stacked cards, not as a labelled container.

8. Left open on purpose

These belong to Stage 3, and a direction that does not take a clear position on each of them is not a direction:

  • Whether the ground stays felt green, and whether it is flat, textured, or lit.
  • The card back. It is currently a procedural navy lattice and is the most obvious candidate for real art.
  • Whether the score readout stays a dense text block or becomes a scannable panel. It is the one screen region where information design matters more than styling.
  • Whether the four action buttons stay a vertical rail on the right edge, which is also the arrangement that fails first in portrait.
  • Type personality, within the four roles fixed in section 4.

9. Decisions needed before Stage 3

  1. Does the felt survive? If green is non-negotiable as the identity, two of the three directions are constrained before they start and it is better to say so now.
  2. How much should the UI teach? The four missing states above are all rule-explaining. Filling them makes the game far more legible to anyone who is not you, and busier for someone who already knows the family rules. That is a product decision, not a visual one.
  3. Card faces: indices only, or full pips? Corner indices are required either way. Pip layouts are considerably more art, and this is a game where the rank matters and the suit only matters for spades and two specific cards.
